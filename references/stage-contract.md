# 단계별 산출물 계약

## 기본 디렉터리

```text
outputs/<project-slug>_<YYYYMMDD>/
├── 00_usage_classification/
├── 01_source_inventory/raw/
├── 02_refined_transcript/
├── 03_source_map_outline/
├── 04_html_report/assets/
├── 05_validation/
└── 06_publish/
```

여러 영상을 별도 페이지로 만들 때는 프로젝트 루트 아래에 영상 ID 또는 안정적인 slug별 하위 폴더를 둔다. 공통 자료만 프로젝트 루트에 둔다.

## 0단계 — 활용 방법 탐색과 분류

최소 산출물: `00_usage_classification.md`

- 영상의 잠재 사용자를 역할별로 분류한다.
- 활용 장면, 즉시 실행 항목, 도입 조건, 위험·검증 필요성을 표로 정리한다.
- “한 문장 결론”과 다음 단계에서 확인할 핵심 주장 목록을 만든다.
- 단순 요약이 아니라 의사결정·실무 적용 관점으로 분류한다.

완료 게이트: 활용 유형마다 사용자·상황·행동·주의점이 연결되어 있다.

## 1단계 — 자료 목록화와 자막 상태 확인

최소 산출물: `01_source_inventory_and_subtitle_status.md`, `raw/` 원본 자료

- 영상 URL, ID, 제목, 채널, 길이, 게시일, 설명, 원어를 기록한다.
- 수동/업로더 자막과 자동 자막을 구분하고 언어·형식·큐 수·롤링 중복 여부를 확인한다.
- 메타데이터, 우선 자막, 원시 자동 자막, 썸네일을 가능한 범위에서 보존한다.
- 원본 파일의 SHA-256을 기록한다.
- 설명란 링크는 영상 제작 소스와 기술 검증 소스로 구분한다.

완료 게이트: 어떤 자막을 주 입력으로 쓰고 다른 트랙을 무엇에 사용할지 결정되어 있다.

## 2단계 — 자막 중복 정리와 시간대별 정제

최소 산출물: `cleaned_cues.tsv` 또는 동등한 정제 큐, `02_timeline_refined.md`

- VTT 태그, 단어 타임태그, 롤링 반복, 연속 공백을 제거한다.
- 문장 경계와 기술 용어를 복원하되 의미를 새로 만들지 않는다.
- 시간 링크가 있는 의미 구간으로 재구성한다. 구간 수는 영상 내용에 맞춘다.
- 정제 전/후 큐 수와 중복 감소율을 기록한다.
- 모델명·수치·지원 범위처럼 검증이 필요한 발화에는 검증 메모만 붙이고, 자막 자체를 공식 사실처럼 고치지 않는다.

완료 게이트: 전체 자막을 빠짐없이 대조했고, 원본에 가까운 큐 표와 읽기 좋은 타임라인이 모두 있다.

## 3단계 — 소스맵과 보고서 목차

최소 산출물: `03_source_map_and_outline.md`

- 출처에 `S01...` ID와 등급을 부여한다. 공식 1차 자료를 최우선으로 둔다.
- 핵심 주장에 `C01...` ID를 부여하고 근거·판정·표현 방식을 연결한다.
- 판정 어휘를 일관되게 사용한다: `공식 확인`, `영상 주장`, `보정`, `미확정`, `분석/권고`.
- 최종 보고서 논지, 독자, 목차, 시각 구조, 상호작용, 접근성, 작성 경계를 설계한다.
- 수치 카드는 반드시 출처를 연결한다.

완료 게이트: 최종 HTML의 각 핵심 결론이 최소 하나의 출처 또는 명시적 분석으로 추적된다.

## 4단계 — HTML 보고서

최소 산출물: `04_html_report/index.html`, 필요한 로컬 `assets/`

- Hero, 핵심 요약, 개념 설명, 정제 타임라인, 활용 지도, 팩트체크, 위험·가드레일, 실행 체크리스트, 출처·방법론을 내용에 맞게 구성한다.
- 영상 요약과 공식 검증을 시각적으로 구분한다.
- 타임코드는 원본 영상의 해당 지점으로 연결한다.
- 반응형·키보드 접근·명도 대비·감소 모션·의미 있는 `alt`를 제공한다.
- 상호작용은 필터·복사·체크리스트처럼 독자의 판단에 실제 도움이 될 때만 넣는다.
- HTML은 JavaScript가 실패해도 본문과 출처를 읽을 수 있어야 한다.
- 여러 영상이 분리 대상이면 HTML도 영상별 파일로 만든다.

완료 게이트: 파일을 로컬에서 파싱할 수 있고 모든 로컬 자산 경로가 존재한다.

## 5단계 — 파일 구조와 브라우저 검증

최소 산출물: `05_validation_report.md`, 데스크톱·모바일 스크린샷, `manifest.sha256`

- 전체 파일 트리를 기록한다.
- HTML 파싱, 제목, 언어, viewport, 이미지 자연 크기, 상대경로를 확인한다.
- 실제 브라우저에서 데스크톱과 390px 안팎 모바일 뷰포트를 검사한다.
- `scrollWidth == clientWidth` 또는 수평 오버플로 0을 확인한다. 코드 블록의 내부 스크롤은 허용한다.
- 필터, 메뉴, 복사, 체크리스트 등 주요 상호작용을 실행한다.
- 콘솔 오류와 깨진 이미지가 없어야 한다.
- 실패를 수정한 뒤 같은 검사를 다시 수행한다.

완료 게이트: 검증 보고서에 PASS/FAIL, 환경, 측정값, 수정 내역이 명시되어 있다.

## 6단계 — GitHub Pages 게시

최소 산출물: `06_publish_record.md`

- [GitHub Pages 게시 절차](github-pages-publishing.md)를 따른다.
- 공개 URL, 저장소, 브랜치, 커밋, workflow run, 라이브 HTTP 상태, 자산 상태를 기록한다.
- 라이브 페이지를 실제 브라우저에서 열어 제목·이미지·오버플로·콘솔을 다시 확인한다.

완료 게이트: 공개 HTML과 필수 자산이 HTTP 200이고 라이브 브라우저 검증이 통과한다.
